# A Million Proposals, One "No"
## SD5913_w02_Zhexian Tao

If by 2026 a single English sentence can generate runnable code, and such systems get better every six months, then sitting in a programming class does look suspicious. We don't seem to be learning a future profession so much as a handicraft that is about to be absorbed by natural language interfaces.

But I don't think this course should be defended with the old line that "the fundamentals still matter." The more honest claim is: most of the specific content in this course may really become obsolete over the course of our careers. The question isn't "Is programming still useful?" but rather: as machines become increasingly capable of generating code on demand, which abilities actually become more important?

My answer is: the ability to translate vague intentions into executable constraints, the ability to read and judge code, and the ability to understand a medium's defaults and push back against them. If programming courses still have a future, it's not because we need to race against machines at writing code, but because we need to retain the position of the author after code has become a material.

Painters understand pigment; photographers understand light. What is the "material" of a generative system? Tokens, probability distributions, sampling temperature, random seeds, context windows, training data bias, API limits, rendering pipelines. Ihde said that technology is never a neutral tool—it shapes your sense of what is possible. If code is written by machines, someone still needs to judge whether it works. What does that person need? Not the ability to memorize APIs, but the ability to read the intentional structure of code: what a variable represents, what a loop is repeating, what a condition is filtering, what a function is encapsulating, where errors will appear. If we can read code, we can see where the intention is realized and where it is betrayed. If we can't read code, we can only look at the result. And the result often looks "about right," yet is always slightly off. Art often dies at exactly that point.

In today's AI market, especially in generative models, there are defaults: default 1920x1080, default centered composition, default smoothness, default high saturation, default "good-looking." If we don't understand the medium, we can only accept these defaults, and end up making a pile of things that reek of "AI." Only by understanding the system can we push back against the defaults: deliberately low resolution, deliberately off-center, deliberately letting the colors get a little dirty, deliberately making the output unreproducible, or deliberately fixing all the seeds. Technical literacy is not letting tools decide for us; it is letting us decide where tools are not allowed to decide for us.

Photography did not end painting, and synthesizers did not end music. In 1965, Frieder Nake and Georg Nees were accused of using machines to replace artists. What happened later? They became pioneers of computer art, while photography and synthesizers changed the artist's role: from executor to selector, director, editor, sound designer.

The similarity this time is: machines are taking over codifiable routine labor. The difference is: they are entering not only images and sound, but also code, text, and cognitive labor; they use natural language as their interface, the barrier to entry is extremely low, and the temptation is enormous. So responsibility becomes more concentrated: Who chooses? Who judges? Who signs? If a machine can generate a hundred proposals, the person who says "No, not this one" becomes more important, not less.

Humans are creatures capable of critical thought. Maybe most of the specific content taught in this kind of course really will become obsolete over our careers. If we believe that, the conclusion is not to stop learning, but to change how we learn: learn the transferable things—problem decomposition, abstraction, debugging, reading documentation, version control, evaluation, systems critique. Specific APIs will die; these abilities will not. A programming course should be like a perspective class in an art school: not to make us perspective painters, but to train the way we see space.

So why are we still here? Because machines being able to write code does not mean we are able to think. We can let machines write code, but we cannot let machines decide for us what deserves to exist. We study programming so that, in a world of on-demand generation, we still possess demand, judgment, and authorial responsibility. Machines can generate a million proposals; we need to become the person who knows why only this one is needed.
